Failure Triage Assistant

02The problem

Why this

A red build is not an answer. It's a question about ownership.

Every failing end-to-end run starts the same way: someone opens the job, scrolls the log, opens a trace, reads the spec, reads the app code — and only then knows whether to page the feature developer, fix the test, hit retry, or check the environment. That first sort is mechanical, and it is where the wait happens.

4

Outcomes that look identical in the log

A wrong assertion, a wrong implementation, a timing race and a server that never booted all surface as the same red X on the same check.

~2.5k

Characters of error text per failure

Message, call log, code frame and per-attempt outcomes — before anyone opens the trace viewer or the source file.

0

Of that reading is judgment

The reading is retrieval. The judgment is one sentence at the end of it: whose problem is this?

The bet: classification is a reading task with a small, closed answer set and evidence available in the repository. That is exactly the shape of work an agent with file access can do, and exactly the shape a human should not be doing at 9am.

03What it does

The product in one pass

Red run in, verdict on the pull request out.

The pipeline distills the Playwright JSON report into a compact failure brief, hands it to a read-only Claude agent that also opens the spec and the application code, and posts one structured verdict per failure — classification, confidence, suspected file:line, the evidence it relied on, and a single next action.

Every verdict must carry

  • Classification — one of exactly four labels, no free text
  • Confidence — high, medium or low; low is a legitimate answer
  • Suspected cause — a real path:line in this repo
  • Evidence — the error text or code it actually read
  • Next action — one concrete step for the owner

What it is not allowed to do

  • Fix anything — tools are Read, Grep, Glob, Write, and the only writable file is the verdict
  • Run the tests — it reasons from the recorded run
  • Decide the build — the job's red or green is set by Playwright alone

Verdict format — the contract in the prompt

## AI Test Failure Triage

**2 failure(s)** — one root cause in app/server.mjs

### 1. summary counts only completed todos
- Classification: product-bug
- Confidence: high
- Suspected cause: `app/server.mjs:14`
- Evidence: expected "0 of 2 done",
  received "2 of 2 done"; summarize() counts
  outstanding todos while the string still
  says "done"
- Next action: count `t.done`, not `!t.done`

Illustrative verdict in the required shape, taken from the real condensed report for the product-bug scenario.

04System design

Architecture

One job, one gate, one writable file.

Triage is a branch inside the existing end-to-end workflow rather than a service beside it. Nothing new to host, no database, no queue — the pipeline's own artifacts are the interface between each stage.

05How we grade it

Evaluation harness

The app exists to be broken in known ways.

An agent that writes confident triage is worthless unless you can check it. So the repository ships a defect injector: it edits the working tree to plant one real, named defect whose correct classification is written down in advance. Run a scenario, read the verdict, compare it to the answer key.

06Answer key

Scenarios

Five defects, five different right answers.

Each one is a plausible real mistake, not a marker: the injector rewrites the source so the code the agent reads carries no sign that anything was planted. Names combine, so a run can present a product bug and a flake at once.

07The hard case

Why classification is not pattern-matching

The same failure, one label apart.

One test in the suite asserts against a deliberately tight 700 ms budget. Under the flaky scenario it fails on timing and passes on retry. Under the product-bug scenario it fails at the same line — but on the value, immediately, every attempt. A triage agent that reads “tight timeout” and stops is wrong half the time.

This is why the condensed brief carries per-attempt outcomes and the received value, not just the last error string — and why the prompt names the evidence that distinguishes a flake: passed on a retry, or an unusually tight timeout against variable latency.

08What we learned

Findings, in the order they forced a change

Every one of these was a bug in the harness, not the model.

  1. An injection seam in the source misleads the agent

    The first graded run put the defect behind an environment-variable branch in app/server.mjs. The agent dutifully blamed the branch — the most suspicious thing on the page — instead of the fault. The injector now rewrites the code so the failure looks like an ordinary mistake. Give an agent the artifact a human would get, not a staged one.

  2. Condense the report; don't hand over the raw JSON

    condense-report.mjs distills the reporter output to titles, file:line, error text capped at 2500 characters, code frames capped at 1200, and attempt outcomes. Small input, higher signal, bounded cost — and the brief is readable by the human who gets paged anyway.

  3. Triage must never mask the test result

    The agent step is continue-on-error, the job fails on red regardless, and when no verdict is produced the comment falls back to the raw failure brief plus diagnostics. A silent agent degrades to today's workflow; it never blocks or green-lights a build.

  4. A green run can still need triage

    Playwright exits 0 when a test fails and then passes on retry, so flakes hide behind a passing check. The gate reads stats.flaky from the report and triages those too — that signal is exactly the one nobody chases.

  5. Model routing is an operational detail with teeth

    Running Claude through Microsoft Foundry means the deployment name must be pinned: the opus/sonnet aliases resolve to a default deployment that may not exist in the resource, and there is no startup check — the run fails on the first request. Passing the workflow's own github_token also skips a GitHub App token exchange that otherwise 401s.

09Guardrails

Cost, blast radius, trust

Bounded by construction, not by good behaviour.

The limits below are enforced by the workflow and the tool allowlist, so they hold whatever the model decides to do on a given run.

Runs only when there's something to triage

Green, non-flaky runs never reach the agent step. Cost tracks failures, not commits.

Read-only, with one exception

--allowedTools Read,Grep,Glob,Write, and the prompt permits writing exactly one file: triage-verdict.md.

Bounded turns and bounded input

--max-turns 20 against a capped brief — a runaway loop ends the step rather than the budget.

No new infrastructure

No service, database or queue. One API key and two variables in repository settings.

Advice, never action

It cannot commit, push, retry, close or merge. A wrong verdict costs a reader ten seconds — it does not touch the code.

Auditable after the fact

Brief, verdict, report and traces upload as artifacts for seven days, so any verdict can be re-examined against what the agent was actually given.

11The ask

Closing

Put it on one real suite and measure the agreement.

The harness works and it is graded against a written answer key. What it hasn't been asked yet is the only question that matters to a team: on our own end-to-end failures, how often does the verdict match what the engineer concluded an hour later?

What I need

  • One product repository with a flaky-enough end-to-end suite, in shadow mode — the agent comments, nobody is required to act on it
  • A Foundry deployment and key for that repository
  • Four weeks of failures, and each owning engineer's actual conclusion recorded alongside the verdict

What that buys

  • An agreement rate per class — the number that decides whether this ships or stops
  • A measured read on triage time saved per red build
  • A prompt tuned on real failures rather than five planted ones
